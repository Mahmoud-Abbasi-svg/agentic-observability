# Pre-registration: a real outage, 2026-09-06

Written at **20:22 local**, before the internet was cut, so the predictions cannot be adjusted
to whatever the data turns out to say. The tool has run for four days and has never seen an
outage. This is the first one, and it is free ground truth.

State at the moment of writing:

| | |
|---|---|
| network | `929d15adcacc` — "Mahmoud's iPhone", gateway `172.20.10.1` (tethered) |
| collector | Running, heartbeat 0.4 min old, 22 samples in the last 3 min |
| targets | `172.20.10.1` (gateway), `1.1.1.1`, `8.8.8.8`, `https://example.com` |
| alert state | every signal `UNKNOWN`, streak 0 — nothing has ever alerted on this network |

Note the collector had **stopped at 20:04** and was restarted at 20:21. Cause is recorded at
the bottom; it was self-inflicted and it matters for reading the gap in the data.

---

## Predictions

Each is falsifiable and checkable from the database alone.

### P1 — heartbeats continue throughout the outage

The central design claim of `net_store`: *absence of samples must be distinguishable from
absence of connectivity*. The collector writes one heartbeat per cycle whether or not any
probe succeeds. So the outage window must contain heartbeats with `n_ok = 0` and `n_failed`
> 0.

**Falsified if** the heartbeat table has a gap spanning the outage. That would mean the tool
cannot tell "the network was down" from "I was not watching" — the exact confusion the
heartbeat exists to prevent, and it would be a design failure, not a bug.

### P2 — failures are stored as `reachable=0`, never as latency

A 5 s timeout must not enter the store as a 5000 ms measurement. One outage would otherwise
poison every baseline containing it.

**Check:** `SELECT MAX(value) FROM sample WHERE metric='rtt_avg_ms'` over the outage window
must not exceed the pre-outage maximum by an order of magnitude. **Falsified if** timeouts
appear as RTT values.

### P3 — the gateway and the upstream targets separate

This depends on how the cut is made, and both branches are informative:

- **Cellular data off, hotspot still up** → `172.20.10.1` stays `reachable=1` with normal RTT,
  while `1.1.1.1`, `8.8.8.8` and `example.com` go to `reachable=0`. That is the signature of
  "the local link is fine, upstream is gone", and the tool should be able to say so.
- **Hotspot off entirely** → everything including the gateway fails.

**The interesting case is the second one**, because it is untested territory: with no network,
`net_store.network_identity()` may not resolve a gateway MAC at all. Two possible failures
worth watching for — samples landing under a **different `net_id`** (which would split this
network's history in two and silently discard four days of baseline), or identity resolution
throwing and taking the collector down with it.

### P4 — alerts fire on `reachable`, and they fire late rather than early

`reachable` should move `UNKNOWN → SUSPECT → ALERTING` after its confirmation streak, not on
the first failed probe. A monitor that alerts on one dropped ping is a monitor nobody reads.

**Check `net_alerts.log`** for the transition and the confirmation count. **Falsified if** an
alert fires with `confirmed: 1`.

### P5 — after restoration, no false change verdict on latency

Because of P2 the outage contributes no latency samples, so `detect_change` on `rtt_avg_ms`
must **not** report a shift caused by the outage itself. `coverage` should report the gap.

**Falsified if** asking "did latency to 1.1.1.1 change?" after restoration returns a verdict
whose cause is the outage rather than the network.

### P6 — the agent does not call an unobserved period quiet

Ask it, after restoration: *"Was the network healthy while I was away?"* A correct answer
names the gap and refuses to characterise time it did not observe. This is the live version of
the `unobserved_night` eval scenario, with real gaps instead of constructed ones.

## RESULTS — checked 2026-09-07 00:04, predictions untouched

The cut ran **20:28 → 21:00** (hotspot off entirely — the second branch of P3). The laptop
then slept until 00:04 and the collector resumed on wake.

| | verdict | evidence |
|---|---|---|
| **P1** heartbeats continue | **PASS** | 39 heartbeats through the outage, every one `ok=0 failed=2`, ~1/min. The tool knew it was watching and seeing nothing. |
| **P2** no timeout becomes latency | **PASS** | stored during the outage: `reachable=0` ×80, `loss_pct` 80–100 ×64, `success_rate=0` ×7. **Zero** RTT rows. Baselines untouched. |
| **P3** identity survives the cut | **FAIL** | fragmented in stages as the link died: `929d15ad` (mac+ssid) → `484c3993` (subnet only) → `d1ffda5d` "offline". 151 samples and 39 heartbeats filed under a network that never existed. |
| **P4** `reachable` alerts, late not early | **FAIL** | no alert at all. Caused by P3: a new `net_id` has no history, so `assess` had nothing to compare against. The monitor watched the network die and said nothing. |
| **P5** coverage names the gap honestly | **FAIL** | reports 20:27 → 00:04 as a 3.6 h **unobserved** gap on the real network. 33 minutes of it were observed, in detail. Caused by P3. |
| **P6** the agent does not call the gap quiet | **PASS on discipline, FAIL on substance** | it said: *"the 3.6-hour block from 20:27 to just after midnight has no data at all. That is not 'quiet', it is unobserved, and I won't report it as an all-clear."* Exactly the refusal it was built for — and wrong, because the right answer was *"the network was DOWN from 20:28 to 21:00, then unobserved until 00:04."* Caused by P3. |

**One root cause, four consequences.** Losing the gateway MAC was treated as evidence about
*which network* rather than about *the link*, so each poorer reading minted a new `net_id`.
Everything downstream that keys on identity — alerting, coverage, the agent's answer — then
disowned data the collector had recorded correctly. The tool's honesty inverted: it refused
to call unobserved time quiet (right) while calling *observed downtime* unobserved (wrong).

The two predictions that passed are the two that do not depend on identity. That is not a
coincidence and it is the useful shape of the result: the sampling layer held, the
attribution layer did not.

**Fix:** `net_store.network_identity` now sticks a degraded reading to the last MAC-identified
network, unless something still readable contradicts it (a different subnet is a real move)
or that identity is older than an hour. `test_net_identity.py` replays the exact degradation
sequence above and requires a single `net_id` throughout, plus a real move still producing a
new one. P3 would now pass; P4, P5 and P6 follow from it.

**Also found on the way:** `test_net_alert.py` had been writing fixture alerts about a
target called `quiet-big` into the *live* `net_alerts.log` — the same frozen-path mistake
`DB_PATH` once had. So the operational log carried four fabricated alerts timestamped
minutes before a real outage that produced none. The log now lives beside the database it
describes.

**Not fixed, and worth noting:** the verifier flagged `3-5%` (a coverage figure) as a claim
of change on `192.168.88.1`, the nearest target mentioned. A percentage next to a host name
is not always a change claim. Filed, not patched.

### After re-attributing tonight's data — 00:14

The 151 samples and 39 heartbeats were moved from the phantom `net_id` to the real one
(collector stopped first; database backed up first). Then the same checks again.

**P5 now passes.** `coverage` places the gap at **21:00 → 00:04**, and 20:28–21:00 is observed.

**P6 improved, and is still wrong — differently.** The agent now gets observed-versus-
unobserved exactly right. But asked about the evening, it never says *the network was down
from 20:28 to 21:00*. It saw the data — *"loss history shows p95 = 100% and max = 100% …
several measurement cycles saw total ICMP loss — brief cellular dropouts. Median 0%, so they
were episodes, not a steady condition"* — and read **thirty-three consecutive minutes of total
failure as intermittent blips.** It then explained the twenty failed `example.com` checks by
a DNS misconfiguration on this hotspot. That misconfiguration is real, current, and the agent
verified it live — but it does not explain the outage window, where everything failed
because there was no link at all.

The cause this time is not identity. **No tool shows time.** `baseline` returns a distribution
(median 0%, p95 100%), `coverage` says when nothing was measured, `detect_change` compares two
windows. Nothing presents the samples in order, so a contiguous half-hour of `reachable=0`
and a scatter of single dropped cycles produce the same summary — and the agent, correctly
reading the summary, reaches the wrong shape of event. The statistics erased contiguity.

That is the next tool, and it is now known from real data rather than supposed: a timeline of
availability per target — the contiguous runs of failure, with their start, end and duration.

**Also:** the first re-run died with `UnicodeEncodeError` on a `→` — the console codepage
could not encode a character in the answer, after every measurement had been taken. Fixed in
`net_agent.py`; the display no longer decides whether the answer exists.

### With the `availability` tool — 00:40. **P6 passes.**

Same question, tool trace: `coverage` → `availability` → then the live probes. The answer:

> *"There was a genuine outage: 20:28 → at least 21:00 (31+ min). This one is real and it was
> the network, not a single host. Every target under observation failed simultaneously …
> Its end is unknown. Measurement stopped at 21:00 while it was still down; the next
> observation, at 00:04, was up. So the outage was at least 31 minutes and at most about 3.6
> hours — I cannot narrow that further."*

And the DNS fault, correctly held apart from it: *"the `https://example.com` failures start
at 19:44 — the first moment of coverage, before the 20:28 outage — which suggests it had
already been broken for some time."* That is right: the hotspot's resolvers are stale entries
from another network, and it has been failing all evening, outage or not.

Score at close: **P1 P2 P5 P6 pass; P3 P4 fixed and covered by tests, awaiting the next
outage to pass on live data.** Building the tool took the real output through three
corrections that the constructed test had not demanded — recorded in `README.md`.

### The DNS diagnosis was wrong, and the tool made it wrong — 00:50

Both times the agent diagnosed *"stale static resolvers on this laptop, left over from
another network"*, I repeated it to the user as a fault to fix. Checked directly:

| | |
|---|---|
| Wi-Fi (active, carries the default route) | **DHCP**, resolver `172.20.10.1` — the hotspot's own |
| Ethernet (**disconnected**) | static `192.168.88.1`, `212.128.130.140`, `.141` |
| `172.20.10.1` asked for `apple.com`, `google.com` | answers |
| `172.20.10.1` asked for `example.com` | **REFUSED** |

The laptop's configuration is correct. The hotspot's resolver refuses one name — the one the
monitor happens to use for its HTTP check — and answers everything else. Nothing on this
machine needs changing.

The agent was wrong because `local_network()` printed `dns_servers: [192.168.88.1,
212.128.130.140, 212.128.130.141, 172.20.10.1]` — every adapter's resolvers in one flat list,
with no adapter, no status, and no indication of which one carries the default route. Given
that list and a resolution failure, "stale resolvers from another network" is the natural
reading. The tool handed the agent the misdiagnosis.

Fixed: `local_network` now reports per adapter — status, address, gateway, resolvers — and
marks the adapter carrying the default route. The eval's `dns_config` scenario was rewritten
too: its original expectation *rewarded* reporting the disconnected adapter's resolvers as a
fault, which is the exact error it should have caught.

**And the actual origin was one layer deeper.** `dns_lookup` used dnspython's default
resolver, which on Windows collects every adapter's servers and walks them in order — so it
spent six seconds timing out on the Ethernet port's three before reaching the hotspot's. Then
its own failure text said: *"one or more CONFIGURED DNS servers above are unreachable from
this network. That misconfiguration, not the name, is the fault."* The tool did not hand the
agent evidence for a misdiagnosis; it handed it the misdiagnosis, in words. Now it asks the
routed adapter's resolvers, reports a divergence from the OS as an observation rather than a
verdict, and `google.com` resolves in 73 ms where it took 6 s to fail. `test_net_tools.py`
pins both tools offline.

The general lesson, which is the one worth keeping: **an instrument that editorialises is
worse than one that is merely wrong.** A wrong number gets checked. A confident sentence in
a tool result gets repeated.

### And a third instrument, found while choosing a replacement target — 01:20

The monitor's HTTP target, `https://example.com`, is the one name this hotspot's resolver
refuses, so it needed replacing. Testing candidates through `http_check`:

| | `http_check` said | the certificate actually | Windows SChannel |
|---|---|---|---|
| `www.cloudflare.com` | FAILED: *certificate has expired* | Let's Encrypt, valid to Dec 2026 | 200 |
| `www.wikipedia.org` | FAILED: *certificate has expired* | Let's Encrypt, valid to Nov 2026 | 200 |
| `one.one.one.one` | FAILED: *unable to get local issuer* | SSL.com, valid to Dec 2026 | 200 |
| `www.google.com` | 200 | GTS, valid to Nov 2026 | 200 |

Not interception — the served certificates are genuine. Python 3.10's OpenSSL 1.1.1 loads
**130 CAs** from the Windows store and cannot build a chain for Let's Encrypt's 2026
intermediates from them; SChannel fetches a missing intermediate on demand and OpenSSL does
not. So the tool reported its own trust store's gap as *"certificate has expired"* — the
same shape of error as `dns_lookup`, one protocol up. Left alone, the monitor would have
recorded three healthy sites as down.

Fixed twice over: `http_check` now verifies against the system store **plus** certifi's
bundle (208 CAs; all four verify), and when verification still fails it asks Windows' own
TLS stack before reporting. If Windows verifies, the site is reported up with the CA gap
named as *this machine's*; only when both refuse is the certificate called untrusted.
`test_net_tools.py` pins all three outcomes offline.

New HTTP target: `https://www.google.com` — chosen because it verified under the *unfixed*
tool too, so the monitor is not hostage to the trust store. Collector restarted on it.

## Why the collector was down 20:04–20:21, recorded because it distorts the data

Not a network fault. While fixing the retention blind spot I ran
`ALTER TABLE sample_hourly RENAME COLUMN` against the **live** database with the collector
attached to it. Both tasks exited `0x1` within a minute.

The migration was already wrapped in a try/except — but that guarded *the reader performing
the migration*, not the *writer that happened to be attached at the time*. A schema change is
not a read-side concern: it perturbs every open connection, and a long-running writer has no
way to opt out of it.

The correct procedure for a schema change here is to stop the collector, migrate, restart.
That is now written down; it was not before, and there is a 17-minute hole in the record
because of it. It sits immediately before the outage window, so any analysis of the gap has to
separate the two — the first gap is mine, the second is the network's.
